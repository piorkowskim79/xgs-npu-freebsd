# The XGS 126: what is known, what is not

Everything upstream measured is on an XGS 116. This page collects what the 126 shares
with it, what differs, and which unknowns block which stage.

## Measured 2026-09-13: first run on a factory XGS 126 (live stick, stock NPU firmware)

Host: SMBIOS product `XGS`, version `126r1`, planar `AMDA0201` (Sophos platform id
`AMDA0201-0001` = XGS 126 in the NPU's own startup script), AMD Ryzen Embedded R1606G,
6 GB, UEFI boot, FreeBSD 15.1-RELEASE GENERIC from the stick, serial console 115200.

| Stage | Result |
|---|---|
| PCI bind, BARs 1M/16M/16M, 16 MSI-X vectors | OK |
| barmap cookie/version, five facilities (GIU BAR0+0, CTRL BAR2+0xefc000, MGMT_NETDEV BAR2+0xefd000, NW_AGENT BAR0+0x4000, RPC BAR2+0xefe000 1 MB) | OK, same layout as the 116 |
| CTRL handshake, DEV_READY (firmware MAC `00:01:02:03:04:05`) | OK |
| mgmt rings, ECHO, capabilities (`max_buf_size 9304`, 1 egress DMA engine) | OK |
| `CC_PF_INIT` … `INIT_DONE`, `CC_PF_ENABLE` (first attempt) | OK; link DOWN at first, `NC_PF_LINK_CHANGE` UP a few seconds later |
| NW_AGENT window (`cafebabe`) appears ~12 s after ENABLE; discovery | 16 records, 14 manageable |
| `mvmgmt0` handshake, NPU answers `ff02::1` | OK; NPU link-local `fe80::7e5a:1cff:febc:48b` (MAC `7c:5a:1c:bc:04:8b`), byte-identical to both XGS 116 units upstream measured: a firmware constant |
| `port1..port10` created, born UP, `tx_packets` counts DHCP discovers | OK |
| **RX from a cabled Port 1 (link LED on)** | **0 frames; no DHCP answer** |

The NW_AGENT discovery table of the 126:

| Record | tag | flags | max MTU | Meaning (from the NPU side, see below) |
|---|---|---|---|---|
| 0 | 0x0000 | 0 | 10210 | internal (NPU `eth0`, the 10G trunk to the switch) |
| 1–4 | 0x0001–0x0004 | MNG | 10210 | **NPU SoC ports `eth1`–`eth4`** (mvpp2, `inband/2500base-x`): four copper jacks driven by the CN9130 itself, not by the switch |
| 5 | 0x8000 | 0 | 10210 | internal (switch CPU port 0) |
| 6–13 | 0x8100–0x8800 | MNG | 10210 | switch ports 1–8: copper Port1–Port8 |
| 14, 15 | 0x8a00, 0x8900 | MNG | 10210 | switch ports 10 and 9: the SFP cages (`xgs-sff-event` reports `F1`/`F2` on `phy9`/`phy8`; which cage is which port is *check*) |

So 8 + 2 + 4 = 14 front ports: the switch is again an 88E6193X (UMSD reads switch id
`0x1930`), and the 126's four extra copper jacks hang off the NPU SoC directly. The
driver's tag scheme (`0x81 + index`) covers the ten switch ports; how frames from
`eth1`–`eth4` are tagged on the trunk is Unverified (nothing has been received yet).
`agnic_nwa.c`'s `mac_set` for tags 1–4 landed on `eth1`–`eth4` (their MAC reads
`02:81:00:00:00:00` on the NPU).

What the NPU runs (root shell over `mvmgmt0` with Sophos's public management key):
Linux 4.14.207-10.22.03 aarch64, root `/dev/mmcblk0p3` read-only (this unit runs slot 3;
upstream's ran slot 2), `/persistent` present. About four minutes after NPU boot, at
the moment of the host driver's handshake, the NPU starts Sophos's data plane:
`NetAgent` (answers NW_AGENT), `UMSD_NPU` (switch driver), and `usfp`, a DPDK flow
processor owning `eth0`–`eth4` (`net_mvpp2`, DSA on `eth0`) and five GIU interfaces
`giu-0`…`giu-4` (`/tmp/usfp_nmp_cfg`: one NIC-PF with 4 queues plus four NIC-VFs), with
a `usfp_rh` kernel module exporting shared tables (`usfp_lif_table`,
`usfp_pport2iface_table`, `usfp_iface2pport_table`, flow/conn tables) that the Sophos
host software programs. Without that host-side programming `usfp` forwards nothing to
the host: RX stays at 0 although the switch port has link. `touch
/tmp/host_breakout_complete` on the NPU changed nothing (`grep` finds no consumer of
that name under `/opt/sophos` or `/etc`).

`NetAgent` logged `fail find SoC port N` / `fail find dest port with tag N` for N = 5–10
while the driver ran its one-shot STATE probe by raw port number: raw numbers address
the SoC ports `eth0`–`eth4` only. That probe has been removed from the driver.

Consequence: the host driver is complete for the control plane and the trunk; the
data path with **stock** firmware needs either the Sophos host→`usfp` configuration
(private RPC over the 1 MB RPC facility, not documented anywhere) or a replacement
data plane on the NPU (upstream's `dp_fwd`, extended for `eth1`–`eth4`). Both are NPU
work; see the experiments in the German project sheet.

## Measured on the 126 (2026-09-13, GRUB `lspci` on a factory unit)

| Address | ID | What |
|---|---|---|
| 00:00.0 | 1022:15d0 | AMD Raven/Banded Kestrel host bridge (Ryzen Embedded R1000) |
| 00:00.2 | 1022:15d1 | AMD IOMMU |
| 00:01.1 | 1022:15d3 | PCIe bridge to bus 01 |
| **01:00.0** | **11ab:7080** | **Marvell, class 0200 Ethernet: the NPU endpoint, the only network device** |
| 02:00.3 | 1022:15e5 | USB xHCI |
| 03:00.0 | 1022:7901 | AMD SATA (AHCI): the 64 GB M.2 is SATA |

No Intel (`8086`) device, no AMD network function (`1022` class `02xx`): the R1000's
integrated 10 GbE MACs are not wired up or are hidden by the BIOS. Boot: GRUB 2.06,
SFOS 22.0 build 411, with an "NPU uboot mismatch" check in the boot messages, i.e. the
NPU has its own bootloader the x86 side compares against.

### Two follow-up experiments, same day

1. **Host reload without reboot** (`kldunload`, `kldload`): the CTRL handshake passes,
   `DEV_MGMT_READY` is still set from the first session, the ECHO times out, and the
   pcinet descriptor holds the previous host's ring pointers with status 0. The NPU keeps
   the first session's rings and does not restart its data plane. Driver change 9 in
   CHANGES-FROM-UPSTREAM.md is the (Unverified) countermeasure.
2. **SFOS booted once, then a software reboot into the stick** (no mains cycle): the
   driver comes up fresh, ECHO OK, `mvmgmt0` ESTABLISHED, datapath live. So a warm
   reboot of the host resets the NPU session; production reboots are fine. RX from the
   cabled Port 1 is **still 0**: whatever SFOS configured in `usfp` does not survive our
   handshake (the NPU restarts NetAgent/UMSD/usfp per host session), so there is no
   "inherit the Sophos configuration" shortcut.

Conclusion for the road map: with stock NPU firmware the front panel stays dark for any
non-Sophos host. The next step is a replacement data plane on the NPU, run from `/tmp`
first (upstream's `dp_fwd`, cross-built; the switch itself can stay under Sophos's own
`UMSD_NPU`/`NetAgent`, which the NPU starts anyway), later extended for `eth1`-`eth4` and
made persistent.

## Measured 2026-09-13, evening: dp_fwd on the NPU delivers RX for the first time

Setup reached over a USB WLAN adapter on the host (`rtwn0`/`wlan0`, home LAN 192.168.2.0/24),
SSH into the host, `mvmgmt0` to the NPU, the Sophos key, and `dp_fwd` (built static on the Pi,
sha `2f247d73...`) relayed to the NPU's `/tmp/dp`.

Sequence: on the NPU `npu-run-dp_fwd.sh start` stopped `usfp` and started `dp_fwd`
(`GIU pkt-echo is started` in 1 s; the three UIO modules were already loaded; `NetAgent` and
`UMSD_NPU` kept running). Then on the host `kldunload if_agnic` + `kldload` to re-drive the
P3 handshake against `dp_fwd`.

What happened:

| Result | Detail |
|---|---|
| P3 handshake against `dp_fwd` | OK: `CC_PF_INIT`..`INIT_DONE`, `ENABLE`, trunk link up |
| NW_AGENT | **no response** (`dp_fwd` does not serve NW_AGENT); driver fell back to the SMBIOS table (14 ports), created `port1`..`port14` |
| **RX from the front panel** | **works, first time ever.** `port1` received real home-LAN traffic; `tcpdump port1` decoded a genuine broadcast `192.168.2.33 > 192.168.2.255`; driver counted frames (prefix byte0 `0x81` = port1), `rx_frames` reached 49 |
| **TX to the front jack** | **does not reach the wire.** The host sent 14 packets onto the trunk (`tx_dropped 0`), but the Pi on the same LAN saw **none** of the `port1` MAC `02:81:00:00:00:01`: host->front egress does not leave the jack |
| Stability | RX then stalled at 49 and `mvmgmt0` to the NPU died after the reload; `dp_fwd` kept running |

**Reading.** RX proves the whole front->NPU->`dp_fwd`->trunk->host path end to end -- the thing
stock `usfp` never did. Two gaps remain, both NPU/forwarder-side:

1. **TX egress.** `dp_fwd` is derived from `giu/pkt_echo`; its host->front path either does not
   inject into the switch or tags the DSA header wrongly for a CPU-origin frame, so the
   Sophos-`UMSD_NPU`-configured switch drops it. This kit's own `dp_swcfg`/`dp_swop` switch
   setup was **not** run (we kept `UMSD_NPU`); the egress DSA path likely needs it.
2. **Session stability after a host reload.** `dp_fwd`, like `usfp`, latches the host's rings
   once. The `kldunload`/`kldload` created a second session; a few frames flowed, then RX and
   the `mvmgmt0` mgmt path desynced. The clean test is to **warm-reboot the host** while
   `dp_fwd` is already running, so the host publishes its rings once against `dp_fwd`.

Recovery is a mains cycle (NPU rootfs read-only, `/tmp` volatile): `usfp` returns.

## Same family as the 116

| Property | 116 (measured upstream) | 126 | Confidence |
|---|---|---|---|
| NPU endpoint | `11ab:7080`, BARs 1M/16M/16M | `11ab:7080`; BARs unmeasured | id measured; BARs expected identical |
| NPU SoC | Marvell CN9130, own Linux 4.14 on eMMC, U-Boot in SPI-NOR | same product family and firmware family | Unverified; the barmap cookie/version at stage 0 tells |
| AGNIC ABI (barmap, CTRL, GIU, NW_AGENT, MGMT_NETDEV) | version 0x5, cookie 0xd0fac10d | expected identical | Unverified |
| Host CPU | not stated upstream | AMD Ryzen Embedded R1000, 6 GB | measured (PCI ids), manual |
| Console | micro-USB + RJ45, NPU on the host's third UART | same connectors; UART mapping *check* | manual |

The endpoint-side protocol is NPU software, not switch hardware, which is why upstream
expects it to match across the line. The host CPU vendor is irrelevant to the driver
(newbus, busdma, MSI-X are the same on AMD).

## Different from the 116

| Property | 116 | 126 | Consequence |
|---|---|---|---|
| Front ports | 8 copper + 1 SFP = 9 | **12 copper + 2 SFP = 14** (2 copper ports are PoE) | port count is a runtime value in this driver (`hw.agnic.nports`, discovery, model table) |
| Pport tags | 0x81..0x89 | 0x81..0x8E expected | demux array sized 32; the NW_AGENT discovery at stage 3 confirms the real tags |
| Switch | one 88E6193X (11 ports: CPU + 8 copper + SFP + 1 unused SerDes) | **unknown**: 14 front ports + CPU do not fit one 11-port part; two chips or a larger SKU | irrelevant to the host driver; decisive for any NPU-side switch bring-up |
| Port names under SFOS | Port1..Port8, PortF1 | Port1..Port12, PortF1..PortF2 (*check*) | naming here stays `port1..port14`; which index is which SFP cage comes out of discovery + a cable |
| PoE | none | two copper ports, 30 W each (*check which*) | PoE control is NPU-side; nothing in this driver touches it |

## The decisive unknown: does stock firmware forward?

Upstream's history on the 116, as far as its docs state it:

1. `if_agnic` against **stock** Sophos NPU firmware reached the CTRL handshake, the
   mgmt echo, NW_AGENT discovery and admin-up, and saw **RX** frames with the
   `0x81pp` + `0xC0..0xFF` prefix ("WIRE FORMAT confirmed live on hardware").
2. Host **TX** to the front jacks was dropped by the stock NPU; the 64-byte header
   fill was varied without success (`tx_hdr_mode` knobs).
3. SFOS's own host driver SSHes into the NPU over `mvmgmt0` and touches
   `/tmp/host_breakout_complete` before the NPU starts forwarding; whether that
   handshake alone would have unblocked TX is not recorded.
4. Upstream then replaced the NPU data plane with its own `dp_fwd` + switch bring-up
   and got DHCP end to end on Linux. That firmware is 116-tuned (8-port loops, SFP on
   lane 9, one 88E6193X at SMI address 2) and lives only in `/tmp` on a factory NPU
   because the rootfs is read-only; a persistent install needs a rootfs of your own,
   which nobody has completed.

For the 126 this means: stages 0 to 3 of [TESTPLAN.md](TESTPLAN.md) are host-only and
safe. If RX works and TX does not, the next experiment is the `host_breakout_complete`
touch over `mvmgmt0` (a file in `/tmp` on the NPU; gone at the next NPU reboot, so it is
reversible). If that does not unblock TX either, the road forks:

- **Stop** and keep the 126 as a Sophos box. The production decision for the branch
  office is not affected either way; that site gets an XG 125 Rev. 3.
- **NPU firmware for the 126**: port upstream's `switch-init` to whatever switch
  topology stage 2 reveals, cross-build `dp_fwd`, and solve the rootfs persistence
  that upstream left open. Weeks, with the loop hazard below.

## Hazard: bridging the front ports

Upstream lost a live LAN on 2026-08-08 when a front port was powered before its VLAN
isolation map was written: the switch's reset default maps every port to every port, so
two cabled front ports briefly became a bridge and looped the network. Their scripts
now write and verify the maps first and refuse to power PHYs otherwise.

Nothing in this repository touches the switch. The stock firmware programs it. But if
NPU-side work ever starts on the 126, that ordering rule is the first thing to carry
over, and the box should be cabled to a throwaway switch until it is proven.

## Hazard: never reset the NPU from the host

An FLR or any PCI reset of `01:00.0` kills the running NPU firmware; recovery is a
mains cycle. The driver contains no reset path; keep it that way. `devctl reset` and
`pciconf -w` on that device are off limits.

## What the first boot must produce

1. `platform:` line: the SMBIOS product/version strings (model table).
2. BAR sizes from `pciconf -lbv`.
3. barmap version/cookie and the five facility windows.
4. The NPU link-local on `mvmgmt0` and its `uname -a`.
5. The NW_AGENT discovery table (`P4a: port[i] ...`): tags, flags, MTUs.
6. From the NPU shell: the platform descriptor under `/opt/sophos/plt/` and the switch
   lines from `dmesg`.

With those six items the 126 page here can be rewritten from "expected" to "measured".
