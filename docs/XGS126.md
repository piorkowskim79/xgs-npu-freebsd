# The XGS 126: what is known, what is not

Everything upstream measured is on an XGS 116. This page collects what the 126 shares
with it, what differs, and which unknowns block which stage.

## Measured on the 126 (2026-09-13, GRUB `lspci` on a factory unit)

| Address | ID | What |
|---|---|---|
| 00:00.0 | 1022:15d0 | AMD Raven/Banded Kestrel host bridge (Ryzen Embedded R1000) |
| 00:00.2 | 1022:15d1 | AMD IOMMU |
| 00:01.1 | 1022:15d3 | PCIe bridge to bus 01 |
| **01:00.0** | **11ab:7080** | **Marvell, class 0200 Ethernet: the NPU endpoint, the only network device** |
| 02:00.3 | 1022:15e5 | USB xHCI |
| 03:00.0 | 1022:7901 | AMD SATA (AHCI): the 64 GB M.2 is SATA |

No Intel (`8086`) device, no AMD network function (`1022` class `02xx`): the R1000's
integrated 10 GbE MACs are not wired up or are hidden by the BIOS. Boot: GRUB 2.06,
SFOS 22.0 build 411, with an "NPU uboot mismatch" check in the boot messages, i.e. the
NPU has its own bootloader the x86 side compares against.

## Same family as the 116

| Property | 116 (measured upstream) | 126 | Confidence |
|---|---|---|---|
| NPU endpoint | `11ab:7080`, BARs 1M/16M/16M | `11ab:7080`; BARs unmeasured | id measured; BARs expected identical |
| NPU SoC | Marvell CN9130, own Linux 4.14 on eMMC, U-Boot in SPI-NOR | same product family and firmware family | Unverified; the barmap cookie/version at stage 0 tells |
| AGNIC ABI (barmap, CTRL, GIU, NW_AGENT, MGMT_NETDEV) | version 0x5, cookie 0xd0fac10d | expected identical | Unverified |
| Host CPU | not stated upstream | AMD Ryzen Embedded R1000, 6 GB | measured (PCI ids), manual |
| Console | micro-USB + RJ45, NPU on the host's third UART | same connectors; UART mapping *check* | manual |

The endpoint-side protocol is NPU software, not switch hardware, which is why upstream
expects it to match across the line. The host CPU vendor is irrelevant to the driver
(newbus, busdma, MSI-X are the same on AMD).

## Different from the 116

| Property | 116 | 126 | Consequence |
|---|---|---|---|
| Front ports | 8 copper + 1 SFP = 9 | **12 copper + 2 SFP = 14** (2 copper ports are PoE) | port count is a runtime value in this driver (`hw.agnic.nports`, discovery, model table) |
| Pport tags | 0x81..0x89 | 0x81..0x8E expected | demux array sized 32; the NW_AGENT discovery at stage 3 confirms the real tags |
| Switch | one 88E6193X (11 ports: CPU + 8 copper + SFP + 1 unused SerDes) | **unknown**: 14 front ports + CPU do not fit one 11-port part; two chips or a larger SKU | irrelevant to the host driver; decisive for any NPU-side switch bring-up |
| Port names under SFOS | Port1..Port8, PortF1 | Port1..Port12, PortF1..PortF2 (*check*) | naming here stays `port1..port14`; which index is which SFP cage comes out of discovery + a cable |
| PoE | none | two copper ports, 30 W each (*check which*) | PoE control is NPU-side; nothing in this driver touches it |

## The decisive unknown: does stock firmware forward?

Upstream's history on the 116, as far as its docs state it:

1. `if_agnic` against **stock** Sophos NPU firmware reached the CTRL handshake, the
   mgmt echo, NW_AGENT discovery and admin-up, and saw **RX** frames with the
   `0x81pp` + `0xC0..0xFF` prefix ("WIRE FORMAT confirmed live on hardware").
2. Host **TX** to the front jacks was dropped by the stock NPU; the 64-byte header
   fill was varied without success (`tx_hdr_mode` knobs).
3. SFOS's own host driver SSHes into the NPU over `mvmgmt0` and touches
   `/tmp/host_breakout_complete` before the NPU starts forwarding; whether that
   handshake alone would have unblocked TX is not recorded.
4. Upstream then replaced the NPU data plane with its own `dp_fwd` + switch bring-up
   and got DHCP end to end on Linux. That firmware is 116-tuned (8-port loops, SFP on
   lane 9, one 88E6193X at SMI address 2) and lives only in `/tmp` on a factory NPU
   because the rootfs is read-only; a persistent install needs a rootfs of your own,
   which nobody has completed.

For the 126 this means: stages 0 to 3 of [TESTPLAN.md](TESTPLAN.md) are host-only and
safe. If RX works and TX does not, the next experiment is the `host_breakout_complete`
touch over `mvmgmt0` (a file in `/tmp` on the NPU; gone at the next NPU reboot, so it is
reversible). If that does not unblock TX either, the road forks:

- **Stop** and keep the 126 as a Sophos box. The production decision for the branch
  office is not affected either way; that site gets an XG 125 Rev. 3.
- **NPU firmware for the 126**: port upstream's `switch-init` to whatever switch
  topology stage 2 reveals, cross-build `dp_fwd`, and solve the rootfs persistence
  that upstream left open. Weeks, with the loop hazard below.

## Hazard: bridging the front ports

Upstream lost a live LAN on 2026-08-08 when a front port was powered before its VLAN
isolation map was written: the switch's reset default maps every port to every port, so
two cabled front ports briefly became a bridge and looped the network. Their scripts
now write and verify the maps first and refuse to power PHYs otherwise.

Nothing in this repository touches the switch. The stock firmware programs it. But if
NPU-side work ever starts on the 126, that ordering rule is the first thing to carry
over, and the box should be cabled to a throwaway switch until it is proven.

## Hazard: never reset the NPU from the host

An FLR or any PCI reset of `01:00.0` kills the running NPU firmware; recovery is a
mains cycle. The driver contains no reset path; keep it that way. `devctl reset` and
`pciconf -w` on that device are off limits.

## What the first boot must produce

1. `platform:` line: the SMBIOS product/version strings (model table).
2. BAR sizes from `pciconf -lbv`.
3. barmap version/cookie and the five facility windows.
4. The NPU link-local on `mvmgmt0` and its `uname -a`.
5. The NW_AGENT discovery table (`P4a: port[i] ...`): tags, flags, MTUs.
6. From the NPU shell: the platform descriptor under `/opt/sophos/plt/` and the switch
   lines from `dmesg`.

With those six items the 126 page here can be rewritten from "expected" to "measured".
